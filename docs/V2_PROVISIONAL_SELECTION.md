# V2 provisional selection checkpoint

`v2Marketplace` accepts authenticated operation `select` with exactly `operation`, `job_ref`, `job_version`, `response_ref`, and stable `intent_key`. It accepts no poster/worker identity from the body. The backend derives the worker from the authoritative response at that job and verifies deterministic response identity, response/job version, submitted/eligible state, current poster and worker standing, and current actionable job/scope/schedule.

One private `v2ProvisionalSelections/{job_ref}` record is created in the same Firestore transaction as the job transition. It records schema/policy version, poster and worker bindings, response, source/result job versions, command digest/idempotency identity, timestamp, and standing provenance. Canonical job lifecycle becomes `SELECTION_PENDING_FUNDING`, financial state becomes `FUNDING_REQUIRED`, and job revision increments once. This records the worker-bound provisional choice required before the next funding checkpoint; it does not implement a funding attempt, monetary snapshot, provider request, assignment, or work authorization.

Exact retries return the original bounded receipt. A reused key with changed input fails `request_conflict`; a different selection after one is recorded fails `already_selected`. Firestore transaction conflicts serialize competing requests. There is no reselection/expiry/reopening operation in this slice; safe terminalization belongs to the later lifecycle checkpoint. Responses are preserved. Pending jobs leave worker discovery but remain visible to their poster, including after the scheduled time passes.

Owner-only posted/detail/response reads expose the safe selection receipt. Response reads also include the selected response independently of pagination. No raw worker UID, private account data, standing provenance, or command digest is projected. Existing worker response retries remain unchanged; no worker notification is sent. Private selection documents inherit existing Firestore default-deny rules.

The iOS repository validates typed receipts and binds them to the submitted job/version/response/key. The ViewModel stages the command synchronously when the poster explicitly confirms, blocks duplicate taps, retains the same command after an uncertain outcome, and preserves responses after operational failure. Reload obtains authoritative selected state; an account change clears private presentation state. A relaunch recovers by reading the backend selection rather than asserting an unconfirmed local choice. Views only render state and forward actions through the existing My Jobs/response UI.

Focused checks: marketplace unit/contract tests, `test-emulator/v2-selection.test.js` concurrency/rules tests, iOS `Scripts/test-v2-marketplace.sh`, and simulator Debug build. The contract test extends real publication → response → poster read → selection → reload without provider/payment calls.

Only `functions:v2Marketplace` requires a future independently authorized selective deployment. No rules/index/configuration change is introduced. No deployment is authorized by this document. Gate 6 remains NOT PROVEN DEPLOYED.

Manual retest after separately authorized activation: publish a supported job; submit responses from two eligible worker accounts; open My Jobs as poster; choose a response and cancel (no mutation); choose and explicitly confirm; verify “Selected · awaiting funding,” no card/payment UI, and no assignment/work-start claim. Reload/relaunch and verify the same response remains selected. Attempt a competing selection from a second poster session and verify rejection plus reload of the winner. Interrupt a selection request and retry the retained command; verify one authoritative selection and one version increment. Worker discovery must no longer offer the selected job for new responses.
